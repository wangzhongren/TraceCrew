# 轮次上限收尾与重复循环防护（把剩余轮次给 AI）——设计方案

> 状态：**设计期，待客户确认**（运行时行为变更按惯例呈批后实施）。
> 客户原话：「已达到最大轮次，把剩余轮次需要给AI。」（另两隐含诉求：循环空转要治、终止要说明白）
> 前提事实：**新派发功能链路本身工作正常**（mode=mapper 咨询被正确调起、卡流正常）——本缺陷是其首跑时暴露的运行时问题，独立立案。

## 1. 立案证据（客户实例现场日志，2026-10-16）

- **重复循环**：首轮 mapper 咨询 Turn 25→50，**连续 26 轮**输出完全相同的 `<search path="…/doudian_im_msg.js">sendMedia</search>`（每轮 122 字符；工具结果恒为 122 字符、零新信息），Turn 50 撞限：`TURN LIMIT reached (50 turns, 50824ms)`。
- **裸终止**：done message = 字面串「已达到最大轮次限制」——客户看到的即此；**零最终产出**（无 call_graph JSON）。
- **重试放大**：随后 `[Mapper 咨询] JSON 解析失败 (第1次)` 起**新一轮完整 50 轮预算**的探索（日志可见第二次同样从 list-dir 重走并在 `doudian_im_msg.js` 上再次进入同类循环）；同构重试共 2 次 → 单次咨询最坏 ≈ 3×50 轮空转。
- 代码根因位：`electron/server/services/agent.ts` processStream 轮次循环（`turn > 50` → 裸 done，≈:869-873）；循环护栏缺失；ChatPanel 咨询重试（`runMapperConsult`）每次新请求均得全量预算。

## 2. 需求解读与目标

1. **收尾轮（核心）**：接近/达到上限时不要裸切断——**把剩余轮次交给 AI 用于收尾**：基于已收集信息产出最终结论/图谱；
2. **重复循环防护（本次一并做）**：连续 N 次「相同操作 + 相同结果」→ 注入纠偏；再犯 → 提前收尾（治本，上限问题大半不再触发）；
3. **终止口径**：真撞限时如实说明（已达上限、已做多少、如何继续），不再用裸字面串。

## 3. 设计（v1）

### 3.1 近限提示（软收尾）
- 触发：`turn >= LIMIT - 3`（剩余 ≤3 轮）时，**调用模型前**注入一条 user 消息：
  「【系统】探索轮次即将用尽（剩余 N 轮）。请开始收尾：不再发起新的探索操作；在剩余轮次内直接给出最终结论/图谱，并在末尾追加 `<final/>`。」
- 目的：让模型自己的最后 2-3 轮转为收尾（"把剩余轮次给 AI"的字面达成）。

### 3.2 硬收尾轮（达限不再裸切）
- 触发：`turn == LIMIT` 时：
  - **不再执行该轮的工具**；改为注入【系统】：「已达探索轮次上限。请立即基于已获得的信息，直接输出最终结论/图谱（不再使用任何工具），并在末尾追加 `<final/>`。」→ 追加**一次**收尾调用（预算外的"第 LIMIT+1 轮"）；
  - 该轮若仍输出操作标签：**忽略执行**，取其正文为最终产出；
  - done.message = 收尾轮清洗后正文；**只要模型有任何可交付内容，用户就拿到结论而非"已达上限"**。
- 兜底：收尾轮也失败/为空 → 走 3.4 的如实终止文案。

### 3.3 重复循环防护
- 每轮记录二元签名：`opSig = JSON.stringify(ops)`、`resSig = 结果长度+头部摘要`；
- **连续 K=3 轮**（opSig,resSig）完全相同 → 注入纠偏 user 消息：「【系统】你已连续 3 次执行完全相同的操作且结果未变化。请改变策略：换关键词/换文件/改用 read-file 直接读取目标区间，或直接基于已有信息给出结论。」→ 重置计数；
- 纠偏累计 **2 次**后仍复现 → **提前进入 3.2 硬收尾**（不等撞限）；
- 常量集中定义（`LOOP_REPEAT_K=3`、`LOOP_MAX_NUDGES=2`、`WRAPUP_RESERVE=3`），后续可调。

### 3.4 终止口径（兜底文案）
- 所有「撞限/提前收尾失败」路径的 done.message 改为结构化如实文案：
  「已达探索轮次上限（{N} 轮，已执行 {M} 次工具操作）。建议：再发送一条消息即可继续，我会带着当前进度接着做。」
- 参数（轮次/操作数）由服务端填充；不再出现裸「已达到最大轮次限制」。

### 3.5 重试预算收窄（治"重试再起全预算"）
- 咨询（及同类）重试请求携带新的可选参数 **`max_turns`**（默认 50；重试建议传 15），服务端 processStream 读取并作为本轮上限；
- 重试提示同时带收尾语义：「请优先基于已收集信息直接输出 call_graph/sequence_graph；确需补充探索，最多 {max_turns} 轮。」；
- 效果：单次咨询最坏 ≈ 50 + 15 + 15 轮，且每次重试都逼近"直接出图"。

### 3.6 范围与排除
- **v1 范围**：`processStream`（chat/stream 各模式：pm/mapper/planner 等，含咨询与主流水线 chat 路径）+ ChatPanel 咨询重试的 `max_turns`；
- **排除**：动作流路径（`runActionStream`，另一处轮次限制）仅归目观察（同类文案统一为可选低风险项，随实施评估）——避免一次动两套终止逻辑。

## 4. 回归与验收

- **注入式假客户端单测**（沿用既有 `frontend/test/agent-pipeline` 或 `test/agent.test.ts` 的替身模式）：① 构造连续重复 ops 序列 → 断言 K 次后出现纠偏注入、二次后提前收尾；② 构造逼近上限序列 → 断言近限提示注入与"硬收尾轮产出即 done.message"；③ 断言终止文案含参数、非字面串；④ 断言 `max_turns` 生效（重试≤15）。
- **真实场景复刻**：对 dkai/dake-ai-kefu 的 `doudian_im_msg.js` 下钻（客户原触发路径，只读、端口可用窗口由协调者安排）——预期：不再空转 26 轮；或在收尾轮产出 call_graph/sequence_graph；最坏撞限时给出如实文案+可继续指引。
- 门禁：四门槛（119/119、tsc/build/check=0）+ 启动冒烟 + **project-test 独立验证** + **客户 GUI 目视**。

## 5. 工作量与风险

- 触点：`agent.ts` processStream（四个注入点 + 常量 + 签名追踪 + max_turns 参数）；ChatPanel `runMapperConsult`（重试传 `max_turns: 15` + 提示文案）；单测新增。量级 **M**。
- 风险：K=3 误伤正常探索（概率低：完全相同的操作+结果三次；纠偏文案本身无害）；收尾轮质量（兜底文案保底）；`max_turns` 参数面小（默认值不变，向后兼容）。

## 6. 未决（请客户确认时一并定）

1. 收尾轮策略默认值：近限提前 3 轮 + 达限追加 1 收尾轮（「把剩余轮次给 AI」的推荐落实方式）；
2. 循环常量 K=3 / 纠偏 2 次即提前收尾（默认）；
3. 重试预算 15 轮（默认）；
4. 动作流路径（ActionPanel 执行）同类风险 v1 不扩、归目观察（默认）。
